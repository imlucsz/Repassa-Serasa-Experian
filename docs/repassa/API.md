# Shared API contract v0.1
Canonical draft `contracts/openapi.yaml` (OpenAPI 3.0.3). Paths relative to `/api/v1`. Coordinate changes with both agents; no unilateral drift. Authenticated endpoints use Bearer JWT; refresh/session cookie is HttpOnly and checked by backend. Public catalog only AVAILABLE items, staff stock separate. IDs UUID, timestamps UTC ISO-8601, enum strings as schema. JSON requests/responses camelCase. List `{items,page,pageSize,total}`. `ErrorResponse`: `{code,message,requestId,fieldErrors?}`; 400 validation, 401 unauthenticated, 403 forbidden (or 404 for hidden resource), 404 missing/inaccessible, 409 transition/availability conflict, 429 rate limit, 503 service unavailable. Avoid raw DB errors. Never expose password hash, digest, refresh token, donor PII, internal storage key to public. DTOs reject unexpected fields. Use no-store on private/auth responses.

## Endpoints overview
- `GET /health`, `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /me`, `PATCH /me`.
- `GET /institutions` public active pickup points; `GET /me/institutions` staff memberships.
- `GET /materials`, `GET /materials/{id}` public available catalog and detail; public unavailable details return 404, private history still accessible to owner/staff.
- `POST /uploads` optional photo multipart, returns uploadId; `POST /donations`, `GET /me/donations`, `POST /donations/{id}/cancel`.
- `POST /materials/{id}/reservations`, `GET /me/reservations`, `POST /reservations/{id}/cancel`.
- `GET /institutions/{institutionId}/dashboard`, `GET /institutions/{institutionId}/materials`, `POST /institutions/{institutionId}/materials/{id}/receive`, `POST /institutions/{institutionId}/materials/{id}/reject`, `POST /institutions/{institutionId}/pickups/confirm`.

Login/register return access token + user, set refresh cookie (register creates student/session). Refresh rotates cookie returns same response; logout revokes current family and clears cookie, 204. Staff registration not public. CSRF origin check: allow only configured same-origin UI for cookie mutations, require `X-Repassa-Request: 1` on all auth POSTs, JSON content type when a body is present, with same-origin policy; reject cross-origin, no broad CORS. Local proxy preserves safe origin/host configuration. Private student endpoints owner-check; staff memberships checked at each request. See SECURITY. Code is present only in own active reservation DTO, nullable otherwise; pickup output returns safe reservationId/materialId/status/completedAt, never student contact info. Institution address is demo public data.

## Institutional administration (DEV-06)
- `POST /institutions` — any authenticated user registers an institution; always created `PENDING` + `isActive=false`, no membership/role granted. Invisible to `GET /institutions` until approved. Duplicate name+address (case-insensitive, non-REJECTED) → 409; REJECTED frees the pair again. Per-user rate limit: 5 registrations/hour → 429.
- Institution lifecycle: `PENDING → APPROVED` (approve, sets `isActive=true`) or `PENDING → REJECTED` (reject, `reason` required, terminal). `APPROVED` ⇄ `isActive` toggled by activate/deactivate. Non-APPROVED can never be activated; only `APPROVED`+`isActive` appear publicly and accept donations/materials/reservations. Deactivation never strands in-flight reservations — owner cancel and staff pickup confirm still complete on a deactivated institution.
- Concurrency: transitions are atomic conditional updates (`updateMany` guarded by current state — incompatible concurrent transitions serialize to one winner + 409 losers). User-scoped mutations (`assignMember`, `revokeMember`, `setUserRole`, `setUserActive`) take a `FOR UPDATE` row lock, keeping membership⇔role and session revocation consistent under parallel requests. Institution lock precedes user lock when both are needed.
- First ADMIN: `DATABASE_URL=... npx tsx scripts/provision-admin.ts` (interactive hidden password or `--generate` one-time random; `--elevate` upgrades an existing account and revokes its sessions; writes `admin.provision` audit). Never a public endpoint, never a demo seed, never a fixed password.
- `GET /admin/institutions` (filters `status`, `isActive`, `q`) returns `AdminInstitution` (adds `status`, `isActive`, `memberCount`, `materialCount`, timestamps).
- `POST /admin/institutions/{id}/approve|reject|activate|deactivate` → `AdminInstitution`; 409 on invalid transition.
- `GET /admin/institutions/{id}/members` → `AdminMember[]`; `POST .../members` `{userId}` → 201 membership + role→STAFF (409 duplicate/ADMIN/inactive user/non-APPROVED institution); `POST .../members/{userId}/revoke` → 204, demotes to STUDENT on last membership (404 missing membership).
- `GET /admin/users` (filters `role`, `isActive`, `q`) → `AdminUser` (never `passwordHash`). `POST /admin/users/{id}/role` `{role: STUDENT|STAFF}` bounded — ADMIN not assignable via API (400) and existing ADMIN rows immutable (409); STAFF→STUDENT drops memberships. `POST /admin/users/{id}/activate|deactivate`; deactivate revokes all refresh sessions immediately; self-deactivation 409.
- `GET /admin/materials` (filters `status`, `institutionId`), `GET /admin/reservations` (`status`, `institutionId`, `studentId`; pickup code never included), `GET /admin/audit-events` (`action` exact or `prefix.`, `institutionId`, `actorId`) — read-only cross-tenant views.
- Audit: `institution.register` and every `admin.*` mutation write an `AuditEvent` (actor, target refs, metadata). No PII beyond ids/emails already listed.
- Permission matrix: public → `GET /institutions`, catalog; authenticated user → `POST /institutions`, own flows; STAFF → institution-scoped receive/reject/confirm for own memberships only; ADMIN → all `/admin/*` (JWT role checked server-side per request; deactivated users 401 immediately).
- Errors follow the shared contract: 400 validation, 401 missing/deactivated token, 403 non-ADMIN, 404 unknown/hidden, 409 transition conflict, 429 throttle.
- Screens needed (frontend/Codex): admin login reuse; pending-institutions queue with approve/reject(+reason); institution list/detail with activate/deactivate + member assign/revoke; user list with role/activation controls; read-only materials/reservations/audit views; institution self-registration form. All under an ADMIN-only nav.
- Limitations: no bulk ops, no admin notifications/email, audit is append-only without retention policy, member list is unpaginated, registration rate limit is per-replica in-memory (fixed-window), duplicate detection is name+address only (same institution resubmitted with different formatting is a separate row for admin review).

## Integration gate
Contract specification is a baseline; implement backend and frontend against exact fields, then run generated Swagger comparison and fixture/live integration. Any added/removed endpoints or changed enum/status/error require shared review. If endpoint not ready, frontend displays explicitly opted-in mock data (`VITE_DATA_MODE=mock` at build time) or an unavailable state. The standalone public demo uses labeled fictional data, and API mode never falls back to fixtures. Test `POST` errors including wrong tenant, concurrency, invalid/expired codes; document changes in DECISIONS. Actual Swagger output may use expanded validation constraints; review compatibility rather than byte equality.
